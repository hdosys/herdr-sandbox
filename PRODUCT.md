# PRODUCT.md

## Purpose

`herdr-sandbox` is a Windows command-line tool for running Windows development and agent workloads inside disposable Windows Sandbox instances. A persistent Herdr server runs in the guest and the Herdr thin client remains on the host, attaching to that server over SSH.

## Terminology

- **Windows Sandbox**: Microsoft's disposable Windows guest environment.
- **Herdr**: the agent-aware terminal multiplexer at `herdr.dev`; its CLI, executable, commands, and version identity remain upstream-compatible as `herdr` and `herdr.exe`. `herdr-win` names only the user's maintained Windows fork/project/release line that supplies Windows remote attach until official upstream builds provide that complete path. Neither project bundles or republishes the other. The future WinGet distribution consists of two independent package IDs, `hdosys.herdr-sandbox` and `hdosys.herdr-win`; after those manifests are published, users may install both in one invocation with `winget install hdosys.herdr-sandbox hdosys.herdr-win`. Before `up` or `attach` mutates lifecycle state, Sandbox verifies the installed host command and rejects missing or unsupported remote behavior with `winget install --id hdosys.herdr-win --exact`. Installation and upgrades remain package-manager owned. This is planned distribution behavior, not a claim that either manifest is currently published.
- **Host**: the user's normal Windows machine.
- **Guest**: the disposable Windows Sandbox instance.

## MVP Behavior

- `herdr-sandbox config` creates only the user-owned `%APPDATA%\herdr-sandbox\config.json` when absent, never replaces an existing file, and asks the Windows Shell to open it with the application registered for `.json` files. It does not open a hard-coded editor or mutate Sandbox lifecycle state. `herdr-sandbox plan` validates and prints the effective configuration, workspaces, stacks, packages, and any exact ready-guest launch-plan differences without seeding configuration or changing app, host-tool, or Sandbox state. `herdr-sandbox init --stack <name>` creates one direct-call project profile at the current project root and never replaces an existing or ancestor-owned profile. `herdr-sandbox up` launches and provisions a fresh Sandbox when none exists. When the exact app-owned Sandbox is already ready with the same fixed workspace mappings, running `up` again re-runs the current Base/project provisioning inside that guest and then reattaches instead of recreating it. `herdr-sandbox attach` verifies and attaches to that exact ready guest without reprovisioning, `status` inspects it, `down` stops it, and `clean` explicitly removes inactive app-owned run workspaces.
- Public host commands use plain, redirect-safe text with descriptive sections, indented fields, deterministic ordering, and one item per line for multi-value results. They do not require color, terminal-width detection, or a TUI framework; errors remain on stderr and command results remain on stdout.
- While provisioning is active, the guest displays the same PowerShell bootstrap in a visible console so progress is observable inside the Sandbox; interacting with that window is not required.
- The guest installs WinGet, installs the pinned Microsoft VC++ runtime required by the Windows Herdr build, copies and verifies the complete compatible Herdr runtime selected on the host, installs/configures OpenSSH Server, selects installed PowerShell 7 as the SSH shell, and starts a persistent Herdr server. Guest provisioning never downloads or installs Herdr through HTTP or WinGet.
- The host authenticates with an app-owned SSH key. The private key stays on the host; only the public key enters the guest.
- Normal interactive `up` success means the host `herdr` client has attached to the guest Herdr server through `herdr --remote`, detached, and verified that the guest server remains running. Installation success or plain SSH alone is insufficient. Explicit `up --no-attach` instead succeeds at the same terminal-ready boundary and leaves the verified guest available for a later `herdr-sandbox attach` or `herdr --remote sandbox`.
- The automatic TUI attach requires real interactive console input, output, and error streams. Without `--no-attach`, a redirected or headless caller fails before cleanup, provisioning, download, or host-tool mutation and points to the intentional headless option; it must never send a live TUI into log files or present a blank terminal as success.
- Fresh guest readiness includes one focused initial guest workspace with a root terminal pane, so remote attach never opens an empty client surface.
- The Sandbox tool never installs, updates, or replaces host Herdr. It resolves the existing standard `herdr.exe` command, verifies Windows remote support and the active physical runtime identity, snapshots that runtime into fresh immutable run input, and copies it into one guest-local directory placed first on the guest machine `PATH` so host and guest use the same version and protocol. Through the real SSH shell it verifies that `herdr.exe` resolves to that copied runtime. Immediately before reporting `up` successful, it also verifies that package management did not replace the host runtime during provisioning. It installs or updates only the `sandbox` alias through the user's standard SSH configuration. The printed `herdr --remote sandbox` command therefore reattaches from any normal host terminal without session-specific PATH or environment setup.
- The CLI does not create a host-side Herdr workspace or pane as a substitute for remote attach.
- Failure names the failed phase and points to bounded, terminal-safe diagnostics. `up` has no overall launch-to-ready deadline unless the user supplies `--timeout`; cancellation and narrower external-operation timeouts remain enforced. Retained reprovisioning publishes live progress and one host-owned bounded current/latest operation result separately from guest readiness, so a failed refresh never erases or falsely downgrades an otherwise ready guest. If a retained operation exits without a terminal result, the next lifecycle-lock owner records it as interrupted before any close, replacement, or cleanup mutation; another operation cannot silently overwrite a still-running record.
- `up` never closes an existing Sandbox automatically. It reuses only an exact ready app-owned guest whose immutable mappings still equal the currently selected workspace set; starting, failed, changed-mapping, unmanaged, or ownership-uncertain stale state is refused with an explicit next action, while a provably gone stale session is handled by the automatic cleanup below. Changed retained plans name the exact differing audio input, audio output, memory, cache, workspace, Tailscale, or launch-contract fields. `status` reports app-owned guest health separately from the current/latest retained operation, including start time, versions/protocol, safe guest workspace identities, bounded recent timings, diagnostics path, warnings, and the next action. It waits only boundedly for the lifecycle lock and may return a stable read-only snapshot while retained reprovisioning owns that lock. `down` is idempotent and, only after retaining handles and revalidating the exact app-owned launcher/client relationship, terminates that process tree without opening the Windows close-confirmation dialog; when stable Tailscale identity is enabled for a ready guest, it first preserves the current identity state and refuses to terminate the guest if that preservation fails. It refuses to stop an unowned or changed process.
- After command syntax is validated, `up`, `status`, and `down` first run the lifecycle-locked automatic cleanup; `clean` invokes that same owner directly and exactly once. It preserves an exact running app-owned Sandbox and deletes only other strictly validated inactive run directories. When process evidence proves that no Windows Sandbox launcher or client remains, it also removes the stale active record, all strictly validated run directories, and the stale app-owned SSH target file. Unmanaged, changed, unsafe, or otherwise uncertain state is refused without deleting its identity, status, failure, or SSH evidence. Help and invalid command lines remain nonmutating. Explicit `clean` retains the same exact run-ID and reparse-point boundaries; unknown entries remain untouched.

## Product Direction

This project is a standalone Windows Sandbox workflow with no external compatibility target.

Prefer the happy path and fast real feedback over broad configuration, compatibility variants, or speculative abstractions.

Until a deliberate semantic-versioning decision replaces it, manually initiated releases use `v0.0.N`, beginning at `v0.0.0`; `N` is the monotonically increasing release ID and advances by one for each release while the major and minor components remain zero.

- Every release offers both a per-user Windows installer and a ZIP download. This installer is a temporary direct sharing/testing path: it installs only `herdr-sandbox.exe`, `base.ps1`, `stacks.ps1`, and `LICENSE.txt`, replaces those four packaged files as one upgrade set with explicit prior-set restoration and incomplete-rollback reporting, seeds `%APPDATA%\herdr-sandbox\config.json` and `user.ps1` only when each file is absent, adds the fixed install directory to the current user's `PATH` only when an effective equivalent entry is absent, records that ownership across upgrades, and registers an uninstaller. Existing `config.json` and `user.ps1` are user-owned and never replaced by install or upgrade. It does not install Herdr/Herdr-Win, an updater, agent integrations, runtime bundles, or unrelated prerequisites. Uninstall never stops a running Sandbox: it removes the entire `%LOCALAPPDATA%\herdr-sandbox` state root, the exact managed SSH include, and the entire currently selected dedicated package/tool cache, then removes the installed application files, an exact `PATH` entry previously added by this installer, and installer registration while preserving unrelated files in the fixed install directory. A running Sandbox remains open but becomes unmanaged and must be closed manually. The unchecked-by-default **Also delete config.json and user.ps1** option controls only whether uninstall additionally removes the entire `%APPDATA%\herdr-sandbox` configuration root; unchecked uninstall preserves that root for reinstall. Unsafe or uncertain removal ownership fails before application removal. Project-owned `.herdr-sandbox\provision.ps1` files and unrelated SSH content remain outside installer ownership.
- Interactive setup follows Welcome/License/Files/Finish. The license page displays Apache License 2.0 before installation. Successful setup ends on a finish page instead of launching a GUI; it explains that the product is a command-line tool, directs the user to open a new terminal and run `herdr-sandbox init` for a new project or `herdr-sandbox up` for an existing profile, and offers one optional link to the product's setup and usage guide. It has no application-launch checkbox or automatic browser action.
- Welcome and Finish share artwork whose sole editable source is root `bg.png`. Five linear-light Lanczos3 renders cover 96/120/144/168/192 DPI at exactly 164x314, 205x393, 246x471, 287x550, and 328x628 pixels. Setup selects the nearest listed scale from its effective system DPI at GUI initialization and displays that bitmap at native size without NSIS stretching, cropping, or alignment scaling.
- The ZIP contains the same four application files at its root and remains a permanent portable release artifact. Neither release format contains Herdr or becomes an input to a combined package.

## Productive Development Guest

- `%APPDATA%\herdr-sandbox\config.json` may declare a name-to-path map of additional project workspaces and an optional `workspaceDiscovery` object whose nonempty absolute `root` contributes each nonexcluded direct child directory as a project. Its `exclude` array contains Go/RE2 regular expressions matched against each child directory name; any match excludes that child. Discovery never recurses or maps the parent itself. Selected and explicit workspaces are mounted without requiring `.herdr-sandbox\provision.ps1`; when that optional script exists it is strictly validated and run. An explicit workspace at the same path keeps its configured name. Independent workspace-validation errors are reported together. The user runs `herdr-sandbox up` anywhere: the nearest ancestor containing `.herdr-sandbox\provision.ps1` becomes the active project and is added or deduplicated; without one, only globally selected workspaces are used. `memoryMB` defaults to 32768 and must be at least 2048; `--memory-mb` overrides it for one run without rewriting the config. Exact booleans `audio` and `audioInput` independently control guest output and host-microphone sharing, and both default false. With both off, playback is muted and the shared audio services are disabled; input opt-in retains those services so microphone applications can work while output remains initially muted. Changing either audio selection requires `down` before the next `up`.
- The same config may set `cacheDirectory` to an absolute, dedicated Herdr Sandbox cache directory on any available drive; it must not be a shared data directory because every uninstall recursively removes the currently selected cache. When omitted or empty, the cache defaults beneath the system-selected temporary directory (`<system-temp>\herdr-sandbox\cache`, normally `%TEMP%\herdr-sandbox\cache`); the guest always sees the selected directory at `C:\HerdrSandbox\cache`. Caching is strictly demand-driven: a normal provisioning run stores only payloads it actually needs, and later normal runs reuse them without downloading those payloads again; no separate warm, prefetch, or scheduled mode exists. The guest caches the immutable WinGet bundle/dependencies, VC++ runtime, OpenSSH MSI, supported WinGet installer payloads, and each concretely resolved Rust distribution by verified digest, then copies executable bootstrap inputs guest-local before use. The host Herdr runtime travels through per-run read-only bootstrap input instead of the persistent package cache. Because Microsoft's layout bootstrapper cannot create a complete layout inside a Windows 10 Sandbox, `herdr-sandbox up` creates or updates the required Visual Studio Build Tools layout automatically on the host only when the selected project needs it and no valid Current layout exists; the guest then revalidates, materializes, and installs that layout offline. A complete cache-hit provisioning run must finish in under five minutes before feature work continues.
- The optional `wingetPackages` object in `%APPDATA%\herdr-sandbox\config.json` customizes the global Base package set through `remove`, `add`, and `versions`: `remove` may name only known non-core defaults, `add` contains exact WinGet package IDs, and `versions` assigns an exact version to a retained or added package. PowerShell 7 remains protected Core tooling. Invalid/conflicting entries, unavailable versions, and failed installation commands fail without silently falling back; omitted versions retain latest-stable behavior. When installation succeeds but WinGet cannot confirm the exact installed ID/version, provisioning emits a clear warning and continues so WinGet correlation defects do not discard an otherwise usable guest. Package-specific functional verification remains strict. Package selection owns installation, not personal configuration copying.
- The optional strict `codingAgentSync` object has exact boolean fields `opencode`, `claudeCode`, `codex`, `githubCopilot`, and `pi`. Every field defaults to `true`, including when the object or a newly introduced field is absent from an existing config; setting one field false prevents discovery and transfer for that agent. Missing host configuration is a clean no-op. The feature copies only approved user-authored configuration and persisted portable authentication, never conversations, history, logs, caches, project trust, arbitrary home content, or machine-bound keyring state.
- A project `.herdr-sandbox\provision.ps1` may directly call the built-in `Install-DotNetStack`, `Install-GoStack`, `Install-NodeStack`, `Install-PythonStack`, `Install-ZigStack`, `Install-RustMSVCStack`, `Install-CargoNextest`, and `Install-Just` functions before or alongside project-specific PowerShell. `Install-DotNetStack` owns only the current modern .NET 10 LTS SDK package (`Microsoft.DotNet.SDK.10`), which includes its modern runtimes; it never installs .NET Framework, an older SDK family, preview SDKs, Visual Studio, or a compatibility path. An omitted version resolves the latest available stable version through the stack's existing package/channel owner and is concretized before cache/install; an explicit .NET version must remain within 10.0, and every explicit version otherwise remains exact and fails without fallback. TypeScript and .NET target frameworks remain project dependency state owned by their project files.
- Release-owned `base.ps1` and `stacks.ps1` supply every built-in provider/adapter and update with the application. `%APPDATA%\herdr-sandbox\user.ps1` is the one seeded-once user-owned global PowerShell extension; the installer seeds it and `config.json` when absent, while portable use retains the same first-mutating-command fallback. Config owns global package selection and project profiles own project-specific behavior.
- The Sandbox and Jobs project profiles are the validated initial consumers of the shared Base/stack model; each profile declares only the stacks and project-specific tools it owns.
- Release-owned `base.ps1` applies the pinned Just the Browser Edge policies plus the complete reviewed, nonvolatile registry delta produced by the privacy/debloat tool and deliberate Windows UI changes, including Explorer Folder Options and taskbar visibility settings that hide Search, Task View, Windows Widgets, News and Interests, and Weather. Review starts from the complete delta and removes only entries proven volatile, runtime-generated, duplicated, or unrelated to the intended user state; it does not sample a short allowlist. The selected disposable-guest profile intentionally includes the explicitly requested ShutUp10++ switches even when the tool marks them not recommended, including restrictions on Defender cloud/security features, SmartScreen, automatic Windows and driver updates, application inventory, KMS online activation, NCSI, telemetry, DRM, and the named Chromium/legacy Edge services. This registry phase is the first guest mutation after bootstrap input validation: it runs before WinGet download and every package/tool installation, reads back every value, and immediately performs one bounded Explorer restart only when an exact value changed.
- Base Development uses the release-pinned WinGet bootstrap to install and verify the latest available PowerShell 7, Git, GitHub CLI, Tailscale, OpenCode, Starship, fzf, ripgrep (`BurntSushi.ripgrep.MSVC`), actionlint (`rhysd.actionlint`), WinDirStat (`WinDirStat.WinDirStat`), File Pilot (`Voidstar.FilePilot`), and matching Windows Terminal edition before user/project scripts run. Every provisioning phase—including bootstrap, Base, user/project/stack scripts, configuration sync, parser adapters, and verification—continues to run exclusively under inbox Windows PowerShell 5.1. PowerShell 7 is Core/Base-owned interactive guest tooling for Herdr, OpenSSH, and Windows Terminal after provisioning; user/project scripts do not own or reinstall it. Base also verifies and loads the release-pinned GeistMono Nerd Font for the disposable guest session. User/project scripts pin a development-tool version only when they define that exact constraint.
- The explicitly selected ShutUp10++ Chromium Edge controls are written from one table to both `HKCU\SOFTWARE\Policies\Microsoft\Edge` and `HKLM\SOFTWARE\Policies\Microsoft\Edge`, matching the complete user-and-machine state observed in ShutUp10++. The remaining pinned Just the Browser controls stay machine-wide only. Device-location denial owns both the supported App Privacy policy and the machine/user ConsentStore values confirmed by the reviewed delta.
- Windows application background execution remains enabled because installed-application refresh and the supported taskbar materialization path are functional behavior; provisioning must not write `BackgroundAccessApplications\GlobalUserDisabled`. The selected privacy profile does disable the separate application-inventory collector through `AppCompat\DisableInventory`.
- The latest stable Tailscale Windows client is installed and version-verified through the existing WinGet MSI cache path. Exact boolean `"tailscale": true` in the global config opts into one stable tagged tailnet host named `herdr-sandbox`; Tailscale must remain in the selected Base package plan. The first enabled `up` requires a one-off preapproved tagged auth key in `HERDR_SANDBOX_TAILSCALE_AUTH_KEY`, consumes it without printing or persisting it, and captures the enrolled identity. Every later fresh Sandbox restores that same device identity, node key, Tailscale IP, and MagicDNS name without user interaction or another auth key. Ready requires exact identity and local-user ownership verification; an unexpected identity or Windows user SID fails closed. With the option omitted or false, Tailscale remains install-only. No Tailscale credential or state is exposed through a Sandbox mapping. This opt-in remains experimental until the backlog's two-fresh-Sandbox identity and peer-connectivity gate passes.
- All app-owned guest-local runtime state lives beneath one understandable `C:\HerdrSandbox` root: `bin`, `runtime`, `state`, `tools`, `toolchains`, `build`, `staging`, and `visual-studio`. The verified Herdr launcher and marker live in `bin`, its active pointer and runtime leases live in `state`, and its dispatcher/payload live under `runtime\<build-id>`. The only persistent host mapping inside that tree is `C:\HerdrSandbox\cache`; app-owned sibling roots must not be created.
- Only after all selected guest configuration has been transferred and verified does bootstrap create exactly one Herdr workspace and root pane for every selected/mounted project root, using that project's `C:\Workspaces\<name>` root as `cwd`; the active project workspace is focused. Guest Git trusts exactly those manifested roots so mapped host ownership does not break normal repository commands, and wildcard safe-directory trust is forbidden.
- Selected host Git configuration, available GitHub CLI configuration and successful authenticated accounts, enabled coding-agent configuration/authentication, an available Herdr `config.toml`, and Windows Terminal settings/schemes are transferred together after project provisioning, Herdr startup, and SSH host verification but before any interactive workspace or shell pane is created. GitHub CLI credentials stored in the host keyring are exported only through the installed `gh` boundary into memory and imported through guest `gh` standard input; tokens are never printed or persisted in host run state. The guest copies preserve the remaining host configuration but make installed PowerShell 7 (`pwsh.exe`) the default for Herdr, OpenSSH, and Windows Terminal and normalize every configured Terminal font to the verified `GeistMono Nerd Font`, so host-only shells and fonts cannot break guest startup; when no host Herdr config exists, the guest receives only that required default-shell setting. The legacy Windows PowerShell 5.1 Terminal profile remains visible and host files remain unchanged. The guest's PowerShell all-host profile initializes Starship. An explicitly dark host Terminal application theme selects Starship's upstream Pastel Powerline preset; an explicitly light theme selects upstream Catppuccin Powerline with its palette changed from the dark default to `catppuccin_latte`. Every copied destination and generated Starship configuration is verified at its standard guest path, imported GitHub CLI accounts are status-verified, and the running guest Herdr server reloads the copied configuration before pane creation and attach; private SSH/GPG keys, unrelated Windows Credential Manager state, logs, runtime sockets, and unrelated home/AppData content remain excluded. The first attached viewport must therefore show the final selected prompt immediately, without `Ctrl+L`, shell restart, or another manual redraw.
- OpenCode, Claude Code, OpenAI Codex CLI, GitHub Copilot CLI, and Pi have fixed out-of-the-box configuration-sync contracts. OpenCode, Claude Code, Codex file-mode credentials, and Pi copy their documented portable credential files when present; Copilot reuses the already imported GitHub CLI accounts. Codex encrypted/keyring credentials and Copilot-native Windows Credential Manager tokens remain machine-bound and require one-time guest authentication. This copy-only support does not install the four new agent CLIs. Guest-managed OpenCode policy continues to force every OpenCode permission to `allow`; no permission policy is invented for the other agents.
- After installing the selected defaults, provisioning applies one complete taskbar pin list through the supported Start Policy CSP in this exact order: Microsoft Edge, File Explorer, File Pilot, Windows Terminal, then WinDirStat. Full-list ownership is required because appended policy pins do not reorder existing/default pins reliably. A matching existing layout is left untouched. Every change is read back exactly, then triggers a second Explorer restart after the independent early Registry-phase restart; failed or matching policy state never triggers that taskbar-owned restart.
- Only explicitly configured project roots are guest-writable under `C:\Workspaces\<name>`. The host home directory and unrelated repositories are not mapped; changing the workspace list requires a fresh Sandbox launch.
- Windows Sandbox has no supported per-instance CPU-priority control, and Windows client Hyper-V does not support per-VM weights, caps, or reserves under its root scheduler. The product therefore has no idle/low-priority mode and does not pretend that changing the launcher process priority controls guest vCPU scheduling.
- The Sandbox project profile installs and verifies the Go and Rust/Windows build tools required by the repositories actually developed in this workflow. Routine provisioning does not rerun repository test, lint, or build suites; acceptance runs representative Go and Rust commands explicitly through the ready Herdr session while project edits persist on the host workspace.
