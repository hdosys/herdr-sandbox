# PRODUCT.md

## Purpose

`herdr-sandbox` is a Windows command-line tool for running Windows development and agent workloads inside disposable Windows Sandbox instances. A persistent Herdr server runs in the guest and the Herdr thin client remains on the host, attaching to that server over SSH.

## Terminology

- **Windows Sandbox**: Microsoft's disposable Windows guest environment.
- **Herdr**: the agent-aware terminal multiplexer at `herdr.dev`; its CLI, executable, commands, and version identity remain upstream-compatible as `herdr` and `herdr.exe`. `herdr-win` names only the user's maintained Windows fork/project/release line, not the produced program. `herdr-sandbox` publishes its own Sandbox release and never republishes `herdr.exe`; until official upstream builds provide the complete Windows SSH remote-attach path, the `herdr-win` repository is the intended owner of a combined package containing one exact Herdr/Sandbox release pair. The future WinGet installer must contain that pair directly rather than use WinGet package-dependency resolution; this installation path is planned but is not current behavior.
- **Host**: the user's normal Windows machine.
- **Guest**: the disposable Windows Sandbox instance.

## MVP Behavior

- `herdr-sandbox up` launches and provisions a fresh Sandbox when none exists. When the exact app-owned Sandbox is already ready with the same fixed workspace mappings, running `up` again re-runs the current Base/project provisioning inside that guest and then reattaches instead of recreating it. `herdr-sandbox status` inspects the app-owned session, `herdr-sandbox down` stops it, and `herdr-sandbox clean` explicitly removes inactive app-owned run workspaces.
- While provisioning is active, the guest displays the same PowerShell bootstrap in a visible console so progress is observable inside the Sandbox; interacting with that window is not required.
- The guest installs WinGet, installs the pinned Microsoft VC++ runtime required by the Windows Herdr build, installs the pinned Herdr Windows artifact produced by the `herdr-win` project, installs/configures OpenSSH Server, selects installed PowerShell 7 as the SSH shell, and starts a persistent Herdr server.
- The host authenticates with an app-owned SSH key. The private key stays on the host; only the public key enters the guest.
- Success means the host `herdr` client has attached to the guest Herdr server through `herdr --remote`, detached, and verified that the guest server remains running. Installation success or plain SSH alone is insufficient.
- The automatic TUI attach requires real interactive console input, output, and error streams. A redirected or headless caller fails explicitly after printing the reusable `herdr --remote sandbox` command and leaves the verified guest running; it must never send a live TUI into log files or present a blank terminal as success.
- Fresh guest readiness includes one focused initial guest workspace with a root terminal pane, so remote attach never opens an empty client surface.
- The Sandbox tool verifies and, when necessary, atomically updates the existing standard host `herdr.exe` command to the same pinned Herdr Windows release used by the guest, and installs or updates the `sandbox` alias through the user's standard SSH configuration. The printed `herdr --remote sandbox` command therefore reattaches from any normal host terminal without session-specific PATH or environment setup.
- The CLI does not create a host-side Herdr workspace or pane as a substitute for remote attach.
- Failure names the failed phase and points to bounded diagnostics. `up` has no overall launch-to-ready deadline unless the user supplies `--timeout`; cancellation and narrower external-operation timeouts remain enforced.
- `up` never closes an existing Sandbox automatically. It reuses only an exact ready app-owned guest whose immutable mappings still equal the currently selected workspace set; starting, failed, stale, changed-mapping, or unmanaged state is refused with an explicit next action. `status` reports the app-owned session as starting, ready, failed, stale, stopped, or unmanaged without changing it. `down` is idempotent and requests an orderly close through the exact owned Sandbox client's main window only after revalidation; when stable Tailscale identity is enabled for a ready guest, it first preserves the current identity state and refuses to close if that preservation fails. It refuses to stop an unowned or changed process and never force-kills a nonresponsive client or triggers crash-report submission as normal shutdown behavior.
- `clean` preserves the exact valid active run and refuses cleanup when a running Sandbox is not owned by that contract. It deletes only inactive run directories with the app's exact run-ID shape after rejecting reparse-bearing paths; unknown entries and unsafe paths remain untouched.

## Product Direction

This project is a standalone Windows Sandbox workflow with no external compatibility target.

Prefer the happy path and fast real feedback over broad configuration, compatibility variants, or speculative abstractions.

Until a deliberate semantic-versioning decision replaces it, manually initiated releases use `v0.0.N`, beginning at `v0.0.0`; `N` is the monotonically increasing release ID and advances by one for each release while the major and minor components remain zero.

## Productive Development Guest

- `%APPDATA%\herdr-sandbox\config.json` may declare a name-to-path map of additional project workspaces and `memoryMB`, which defaults to 32768 and must be at least 2048. The user runs `herdr-sandbox up` anywhere: the nearest ancestor containing `.herdr-sandbox\provision.ps1` becomes the active project and is added or deduplicated; without one, only globally configured workspaces are used. `--memory-mb` overrides the configured memory for one run without rewriting the config.
- The same config may set `cacheDirectory` to an absolute directory on any available drive. When omitted or empty, the cache defaults beneath the system-selected temporary directory (`<system-temp>\herdr-sandbox\cache`, normally `%TEMP%\herdr-sandbox\cache`); the guest always sees the selected directory at `C:\HerdrSandbox\cache`. Caching is strictly demand-driven: a normal provisioning run stores only payloads it actually needs, and later normal runs reuse them without downloading those payloads again; no separate warm, prefetch, or scheduled mode exists. The guest caches the immutable WinGet bundle/dependencies, VC++ runtime, Herdr archive, OpenSSH MSI, supported WinGet installer payloads, and pinned Rust distribution by their verified digests, then copies executable bootstrap inputs guest-local before use. Because Microsoft's layout bootstrapper cannot create a complete layout inside a Windows 10 Sandbox, `herdr-sandbox up` creates or updates the required Visual Studio Build Tools layout automatically on the host only when the selected project needs it and no valid Current layout exists; the guest then revalidates, materializes, and installs that layout offline. A complete cache-hit provisioning run must finish in under five minutes before feature work continues.
- The optional `wingetPackages` object in `%APPDATA%\herdr-sandbox\config.json` customizes the global Base package set through `remove`, `add`, and `versions`: `remove` may name only known non-core defaults, `add` contains exact WinGet package IDs, and `versions` assigns an exact version to a retained or added package. PowerShell 7 remains protected Core tooling. Invalid/conflicting entries and unavailable versions fail without silently falling back; omitted versions retain latest-stable behavior. Package selection owns installation, not personal configuration copying.
- The optional strict `codingAgentSync` object has exact boolean fields `opencode`, `claudeCode`, `codex`, `githubCopilot`, and `pi`. Every field defaults to `true`, including when the object or a newly introduced field is absent from an existing config; setting one field false prevents discovery and transfer for that agent. Missing host configuration is a clean no-op. The feature copies only approved user-authored configuration and persisted portable authentication, never conversations, history, logs, caches, project trust, arbitrary home content, or machine-bound keyring state.
- A project `.herdr-sandbox\provision.ps1` may directly call the built-in `Install-GoStack`, `Install-NodeStack`, `Install-PythonStack`, `Install-ZigStack`, `Install-RustMSVCStack`, `Install-CargoNextest`, and `Install-Just` functions before or alongside project-specific PowerShell. Optional exact versions fail when unavailable or unsupported; TypeScript remains project dependency state pinned by `package.json` and its lockfile.
- The Sandbox and Jobs project profiles are the validated initial consumers of the shared Base/stack model; each profile declares only the stacks and project-specific tools it owns.
- The global `%APPDATA%\herdr-sandbox\base.ps1` applies the pinned Just the Browser Edge policies plus the complete reviewed, nonvolatile registry delta produced by the privacy/debloat tool and the user's deliberate Windows UI changes, including Explorer Folder Options and disabling Windows Widgets, News and Interests, and their weather/taskbar entry points. Review starts from the complete delta and removes only entries proven volatile, runtime-generated, duplicated, or unrelated to the intended user state; it does not sample a short allowlist. The selected disposable-guest profile intentionally includes the explicitly requested ShutUp10++ switches even when the tool marks them not recommended, including restrictions on Defender cloud/security features, SmartScreen, automatic Windows and driver updates, application inventory, KMS online activation, NCSI, telemetry, DRM, and the named Chromium/legacy Edge services. This registry phase is the first guest mutation after bootstrap input validation: it runs before WinGet download and every package/tool installation, and restarts Explorer only when an exact registry value changed. A later Base phase installs and verifies the latest stable PowerShell 7, WinGet Git, GitHub CLI, Tailscale, OpenCode, Starship, fzf, ripgrep (`BurntSushi.ripgrep.MSVC`), and matching Windows Terminal edition before project scripts run. Every provisioning phase—including bootstrap, Base, project/stack scripts, configuration sync, parser adapters, and verification—continues to run exclusively under inbox Windows PowerShell 5.1. PowerShell 7 is Core/Base-owned interactive guest tooling for Herdr, OpenSSH, and Windows Terminal after provisioning; it is never a provisioning interpreter and no project script owns or reinstalls it. Before Terminal installation Base also downloads the official pinned GeistMono Nerd Font archive, verifies its release checksum, and loads the `GeistMono Nerd Font` family for the disposable guest session. Project scripts pin a development-tool version only when the project itself defines that constraint.
- The explicitly selected ShutUp10++ Chromium Edge controls are written from one table to both `HKCU\SOFTWARE\Policies\Microsoft\Edge` and `HKLM\SOFTWARE\Policies\Microsoft\Edge`, matching the complete user-and-machine state observed in ShutUp10++. The remaining pinned Just the Browser controls stay machine-wide only. Device-location denial owns both the supported App Privacy policy and the machine/user ConsentStore values confirmed by the reviewed delta.
- Windows application background execution remains enabled because installed-application refresh and the supported taskbar materialization path are functional behavior; provisioning must not write `BackgroundAccessApplications\GlobalUserDisabled`. The selected privacy profile does disable the separate application-inventory collector through `AppCompat\DisableInventory`.
- The latest stable Tailscale Windows client is installed and version-verified through the existing WinGet MSI cache path. Exact boolean `"tailscale": true` in the global config opts into one stable tagged tailnet host named `herdr-sandbox`; Tailscale must remain in the selected Base package plan. The first enabled `up` requires a one-off preapproved tagged auth key in `HERDR_SANDBOX_TAILSCALE_AUTH_KEY`, consumes it without printing or persisting it, and captures the enrolled identity. Every later fresh Sandbox restores that same device identity, node key, Tailscale IP, and MagicDNS name without user interaction or another auth key. Ready requires exact identity and local-user ownership verification; an unexpected identity or Windows user SID fails closed. With the option omitted or false, Tailscale remains install-only. No Tailscale credential or state is exposed through a Sandbox mapping. This opt-in remains experimental until the backlog's two-fresh-Sandbox identity and peer-connectivity gate passes.
- All app-owned guest-local runtime state lives beneath one understandable `C:\HerdrSandbox` root: `runtime`, `tools`, `toolchains`, `build`, `staging`, and `visual-studio`. The only persistent host mapping inside that tree is `C:\HerdrSandbox\cache`; app-owned sibling roots must not be created.
- Only after all selected guest configuration has been transferred and verified does bootstrap create exactly one Herdr workspace and root pane for every selected/mounted project root, using that project's `C:\Workspaces\<name>` root as `cwd`; the active project workspace is focused. Guest Git trusts exactly those manifested roots so mapped host ownership does not break normal repository commands, and wildcard safe-directory trust is forbidden.
- Selected host Git configuration, GitHub CLI configuration and successful authenticated accounts, enabled coding-agent configuration/authentication, Herdr `config.toml`, and Windows Terminal settings/schemes are transferred together after project provisioning, Herdr startup, and SSH host verification but before any interactive workspace or shell pane is created. GitHub CLI credentials stored in the host keyring are exported only through the installed `gh` boundary into memory and imported through guest `gh` standard input; tokens are never printed or persisted in host run state. The guest copies preserve the remaining host configuration but make installed PowerShell 7 (`pwsh.exe`) the default for Herdr, OpenSSH, and Windows Terminal and normalize every configured Terminal font to the verified `GeistMono Nerd Font`, so host-only shells and fonts cannot break guest startup; the legacy Windows PowerShell 5.1 Terminal profile remains visible and host files remain unchanged. The guest's PowerShell all-host profile initializes Starship. An explicitly dark host Terminal application theme selects Starship's upstream Pastel Powerline preset; an explicitly light theme selects upstream Catppuccin Powerline with its palette changed from the dark default to `catppuccin_latte`. Every copied destination and generated Starship configuration is verified at its standard guest path, imported GitHub CLI accounts are status-verified, and the running guest Herdr server reloads the copied configuration before pane creation and attach; private SSH/GPG keys, unrelated Windows Credential Manager state, logs, runtime sockets, and unrelated home/AppData content remain excluded. The first attached viewport must therefore show the final selected prompt immediately, without `Ctrl+L`, shell restart, or another manual redraw.
- OpenCode, Claude Code, OpenAI Codex CLI, GitHub Copilot CLI, and Pi have fixed out-of-the-box configuration-sync contracts. OpenCode, Claude Code, Codex file-mode credentials, and Pi copy their documented portable credential files when present; Copilot reuses the already imported GitHub CLI accounts. Codex encrypted/keyring credentials and Copilot-native Windows Credential Manager tokens remain machine-bound and require one-time guest authentication. This copy-only support does not install the four new agent CLIs. Guest-managed OpenCode policy continues to force every OpenCode permission to `allow`; no permission policy is invented for the other agents.
- After installing the selected Windows Terminal edition, provisioning pins that exact package to the current user's taskbar through the supported Start Policy CSP. A matching existing policy is left untouched; a changed policy is read back and followed by one bounded Explorer restart so the pin is visible in the already signed-in guest.
- Only explicitly configured project roots are guest-writable under `C:\Workspaces\<name>`. The host home directory and unrelated repositories are not mapped; changing the workspace list requires a fresh Sandbox launch.
- The Sandbox project profile installs and verifies the Go and Rust/Windows build tools required by the repositories actually developed in this workflow. Routine provisioning does not rerun repository test, lint, or build suites; acceptance runs representative Go and Rust commands explicitly through the ready Herdr session while project edits persist on the host workspace.
